# Incident: v1.3.0 frontend GHCR manifest became unavailable

**Date detected:** 2026-09-13  
**Repository:** `baobab-platform/baobab-dev`  
**Affected published contract:** `ghcr.io/baobab-platform/baobab-dev:1.3.0-frontend`  
**Affected downstream consumer observed:** `baobab-platform/zuribeans` GitHub Codespaces

## Summary

A ZuriBeans Codespace failed to create its configured development container because GHCR returned `No manifest found for ghcr.io/baobab-platform/baobab-dev:1.3.0-frontend`. GitHub Codespaces consequently created its Alpine recovery container, which explained the apparent absence of Node.js, npm, Corepack, and pnpm.

The v1.3.0 Baobab Dev Container release pipeline did **not** fail to publish the frontend image. The release-time evidence shows that the frontend multi-architecture OCI index was successfully created, tagged, resolved from GHCR, signed, attested, and independently verified on 2026-09-04. The tag therefore existed at publication time and became unavailable afterward.

## Release-time evidence

The v1.3.0 workflow run (`33854763946`) published the frontend target under these tags:

- `1.3.0-frontend`
- `1.3-frontend`
- `1-frontend`
- `latest-frontend`

All resolved to the same multi-architecture index digest at publication time:

`sha256:9eab7cb8a4d79fcce515e251c3d59dec47aa6b805c53efe8db6d7a6804fc6a1e`

The publish job then successfully:

1. read the just-published primary tag back from GHCR with `crane digest`;
2. applied the additional semver/latest tags to the same digest;
3. extracted the BuildKit-generated provenance and SBOM material from the merged index;
4. created keyless Cosign signature and attestations;
5. ran `scripts/verify-image.sh` against the immutable digest; and
6. exported the verified tag/digest pair used to generate the GitHub Release body.

The combined release job consumed those exported publication records and accurately recorded the pull directive and digest that were valid at that time.

## Detection-time evidence

On 2026-09-13 GitHub Codespaces attempted:

`docker pull ghcr.io/baobab-platform/baobab-dev:1.3.0-frontend`

The Dev Containers CLI reported that no manifest could be found for the tag and failed container creation. Codespaces then explicitly entered recovery mode and pulled `mcr.microsoft.com/devcontainers/base:alpine`.

This is why inspecting the resulting terminal showed Alpine Linux and no project Node.js toolchain: that environment was the Codespaces recovery container, not the Baobab frontend image.

## Root-cause conclusion

The repository and Actions evidence establish the failure boundary precisely:

- **Not a build failure:** both frontend architecture builds succeeded.
- **Not a manifest-publication failure:** GHCR returned and resolved the frontend index digest during the publish job.
- **Not a release-body fabrication:** the release body was generated from publication artifacts emitted only after successful publish and digest verification.
- **Not a ZuriBeans Dev Container configuration parsing problem:** Codespaces read the configured image reference and attempted to pull it.
- **Failure occurred after publication:** the previously valid GHCR tag/index was subsequently removed or otherwise ceased to exist in the registry.

No workflow currently present in `baobab-platform/baobab-dev` deletes GHCR versions, and the repository history after v1.3.0 contains no package-cleanup change explaining the disappearance. The exact actor or organization-level mechanism that removed the registry object cannot be established from repository/Actions evidence alone. Determining that actor requires GHCR/package or organization audit evidence outside this repository's observable history.

## Control gap

`publish.yml` strongly verifies release correctness **at publication time**, but the project had no control that continuously verified the durability of the pull contracts advertised by a GitHub Release. A registry-side deletion occurring later could therefore remain undetected until a downstream consumer attempted to create a container.

Digest-only signature and attestation verification also cannot detect the later disappearance of a human-readable release tag unless that tag is re-resolved after publication.

## Corrective action

Add `.github/workflows/registry-integrity.yml` with two complementary triggers:

- after `Publish Baobab Dev Container` completes; and
- once per day, plus manual dispatch.

For the latest stable GitHub Release, the integrity workflow parses the exact `docker pull` contracts and recorded digests from the release body and verifies that each:

1. still resolves in GHCR;
2. resolves to the exact digest recorded in the immutable release;
3. has a readable OCI index;
4. contains Linux amd64 and arm64 image manifests; and
5. references child manifests that themselves remain retrievable.

This converts silent registry drift into a visible CI failure without weakening existing signing, provenance, SBOM, or immutable-release controls.

## Release recovery

Do not mutate or silently reconstruct the immutable v1.3.0 release contract. After the integrity control is merged and the registry publication path is revalidated, publish a new reviewed patch release and migrate downstream consumers to that verified release.

A later package-retention or organization-level cleanup policy must preserve any image version still referenced by a supported release or downstream Dev Container. If external audit evidence identifies such a policy as the deletion mechanism, that policy must be changed separately; repository CI cannot prevent an authorized out-of-band deletion, only detect it promptly.
